# 问题闭环、覆盖扩面与责任规则

## 目的

每个问题先确认“清单是否覆盖、测试是否覆盖、覆盖是否真的执行了”，再修复。禁止只围绕截图中的一个按钮或一个报错做局部补丁；同一状态机、页面、入口、数据链和平台差异必须作为一个批次评估。

这里的责任是**角色对交付物的责任**，用于让问题能被及时拦下和修复，不用于事后归咎个人。

## 每个问题的固定流程

1. **复现并固定预期**：记录路由、前置状态、操作、实际/预期、浏览器与 OS；不得含密钥、配对码或用户数据。
2. **查清单**：先查对应领域的发布清单与页面操作清单。若已有行，标记该行是 `PASS`、`FAIL`、`PARTIAL` 还是 `NOT RUN`；若没有行，先新增行，不能直接开始改代码。
3. **查自动化覆盖**：把清单行映射到具体测试文件和断言。区分 helper/unit、API/integration、真实浏览器 E2E；后两者不能由前一层替代。
4. **从点扩大到面**：按下方扩面矩阵检查同组件、同页面、同状态机及相邻入口；先形成 defect 批次，再按根因集中修复。
5. **实现与回归**：开发修复根因并补最小有效回归；QA 独立运行本次清单行及相关回归。任何未覆盖或失败的 P0 行都阻断合并/发布。
6. **记录结论**：在清单写明命令/测试、结果、证据摘要、缺陷 ID、责任角色、未验证边界和下一步。只有本行证据齐全才能写 `PASS`。

## 从一个症状扩大到整个面的检查矩阵

| 维度 | 必查内容 | 例：同步配对码未出现 |
| --- | --- | --- |
| 直接操作 | 点击、提交、成功结果是否可见 | 输入密码后是否立刻出现配对码卡片。 |
| 状态机 | 首次、已配置、禁用、加载、失败、重试、取消/返回 | 首次启用、已启用后重新生成、服务启动失败、空码、关闭后重开。 |
| 相邻动作 | 同一个组件中的其他按钮、入口和返回路径 | “加入设备”、粘贴配对码、替换同步密码、刷新概览。 |
| 数据/API | 请求顺序、错误体、并发和持久化边界 | 保存密码 → 启动 listener → 创建 pairing 的顺序；失败不能伪造成功。 |
| 页面/路由 | 直接进入、导航进入、keep-alive/刷新、首次加载 | `/settings?section=sync` 直接进入与从设置导航进入。 |
| 展示 | loading、error、empty、文案、可访问性、窄屏/深色 | 失败有可见错误；按钮禁用合理；小屏不截断；无无效快捷操作。 |
| 安全与隔离 | secret、pairing code、真实 HOME/端口、日志 | 测试使用临时 HOME/端口 0；断言不输出密码或完整配对码。 |
| 平台 | macOS、Linux、Windows 的路径、shell、权限差异 | 不依赖 `/bin/sh`；Windows 可运行同一测试。 |

任何一项受影响但未验证，应在清单标 `PARTIAL` 或 `BLOCKED`，不能写“全部通过”。

## 覆盖层级与不可替代关系

| 层级 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| Unit/helper | 纯状态转换、校验、错误传播 | React 渲染、按钮事件、真实请求顺序。 |
| API/integration | 后端契约、持久化、协议和错误状态 | 浏览器是否把结果展示给用户。 |
| Component test | 单组件渲染和事件 | 实际路由、应用初始化、真实服务交互。 |
| Browser E2E | 用户从页面入口完成操作、DOM/可见状态和网络顺序 | 真实第三方账户权限或外部服务 SLA。 |
| 真实设备 smoke | 发布产物、真实 Agent/同步环境的最小确认 | 自动化回归矩阵。 |

安全、同步、密钥、配对和不可逆操作的成功路径、失败路径都至少需要 integration + 隔离 Browser E2E；只有 unit/integration 的状态是 `PARTIAL`。

## 责任与认领

| 情况 | 主责角色 | 协作角色 | 必须交付 |
| --- | --- | --- | --- |
| 代码/状态机/数据契约缺陷 | 开发 | QA | 根因说明、影响面、修复、回归测试。 |
| 已有功能但清单没有行，或测试层级不足 | QA | 开发 | 新清单行、覆盖差距、阻断等级；开发补对应自动化。 |
| 清单有行却没有执行、或证据不足仍放行 | QA | 发布负责人 | 更正状态、阻断发布、补执行证据。 |
| 需求/验收条件没有定义 | 产品/CEO | QA、开发 | 明确可观察的预期与优先级，再写清单。 |
| 现有设计系统内的样式/文案实现偏差 | 开发 | QA | 按现有组件/设计 token 修正并视觉回归。 |
| 新交互、信息层级或视觉规范本身未定义 | UI | 产品/开发/QA | 设计规格、组件状态和验收点。 |

UI 不应因为普通卡片样式或已有规范内的实现缺陷被默认拉入；只有设计本身不明确或发生设计变更时才介入。

## 缺陷记录模板

```text
Defect ID:
候选 SHA / 页面或领域:
复现前置状态与操作（无密钥/配对码）:
预期 / 实际:
清单行: 已有 / 新增；当前状态:
现有测试: 文件、层级、覆盖到/遗漏:
扩面结果: 同组件 / 状态机 / 相邻动作 / 路由 / 平台:
根因分类: UI state | API contract | persistence | async order | isolation | design spec | other
主责角色 / 协作角色:
修复批次与新增回归:
统一复验范围与结果:
未验证边界 / 发布结论:
```

## 运行与维护规则

- 新问题先更新清单，再开始修复；紧急修复也必须在同一工作日补齐记录。
- 一个页面出现问题时，先运行该页全部相关行；若根因跨页面（如应用初始化、鉴权、缓存），扩大到共享入口与所有消费者。
- 浏览器 E2E 必须使用临时 `HOME`/`USERPROFILE`、随机端口、`finally` 清理 listener；不得读取真实密钥或占用 3780。E2E 结束前检查端口没有遗留 fixture。
- 每轮结果保留历史，不把旧 `PASS` 复制为新候选的结论。代码、测试、设计或依赖有改动时，相关行回到 `NOT RUN`。
